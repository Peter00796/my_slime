\section{Research Motivation \& Background}
\label{sec:motivation}
% ══════════════════════════════════════════════

Group Relative Policy Optimization (GRPO) has emerged as a leading algorithm for
post-training large language models on mathematical reasoning tasks. Unlike
standard PPO which constrains the policy via a KL penalty term against a
reference policy, GRPO in its purest form sets the KL coefficient to zero
($\lambda_{\mathrm{KL}} = 0$), relying solely on importance-weight clipping to
prevent excessive policy updates.

This design choice raises a fundamental question: \textbf{how off-policy does
the training data become over the course of training, and does this
off-policyness threaten training stability?}

In on-policy reinforcement learning, the data used to compute policy gradients
is generated by the current policy $\pi_\theta$. In practice, however, there is
always a gap between the data-generating policy $\pi_{\mathrm{old}}$ (the policy
at rollout time) and the policy $\pi_\theta$ at training time. This gap grows
with each gradient step taken on the same batch of rollout data. We term this
gap \emph{offlineness}.

Off-policy data degrades the importance sampling estimates that underpin policy
gradient methods. When the importance weights $w_i = \pi_\theta(a_i \mid s_i) /
\pi_{\mathrm{old}}(a_i \mid s_i)$ deviate significantly from 1, the effective
sample size drops, gradient variance increases, and the policy may collapse.

\section{Offlineness Metrics}
\label{sec:metrics}
% ══════════════════════════════════════════════

We instrument SLIME's training loop with four metrics that quantify offlineness
from complementary perspectives. All metrics are computed per microbatch during
the policy loss computation, using per-token importance weights:
\[
  w_i = \frac{\pi_\theta(a_i \mid s_i)}{\pi_{\mathrm{old}}(a_i \mid s_i)}
      = \exp\!\bigl(\log\pi_\theta(a_i \mid s_i) - \log\pi_{\mathrm{old}}(a_i \mid s_i)\bigr)
\]
where $\pi_{\mathrm{old}}$ denotes the policy at \emph{rollout time} (data
generation), not the start of the current PPO epoch.

\subsection{Effective Sample Size Ratio (ESS)}

The ESS measures how efficiently the importance-weighted samples approximate
on-policy data:
\begin{equation}
  \mathrm{ESS} = \frac{\bigl(\sum_{i=1}^{N} w_i\bigr)^2}{N \cdot \sum_{i=1}^{N} w_i^2}
  \label{eq:ess}
\end{equation}
The ratio is normalized to $[0, 1]$: a value of 1.0 means perfectly on-policy
(all weights equal), while values approaching 0 indicate severe off-policy
degradation where a few samples dominate the gradient estimate.

\subsection{Mismatch KL ($\chi^2$ Divergence Proxy)}

We use a second-order approximation to the KL divergence:
\begin{equation}
  D_{\mathrm{mismatch}} = \frac{1}{2}\,\mathbb{E}\bigl[(w_i - 1)^2\bigr]
  \label{eq:mismatch_kl}
\end{equation}
This is equivalent to the $k_3$ KL estimator and penalizes large importance
weights quadratically. It is more sensitive to outlier weights than the standard
KL divergence.

\subsection{Clip Fraction}

The fraction of tokens whose importance weight falls outside a reference
interval:
\begin{equation}
  \mathrm{clip\_frac} = \frac{1}{N}\sum_{i=1}^{N}
    \mathbf{1}\!\bigl[w_i \notin [0.8,\; 1.2]\bigr]
  \label{eq:clip_frac}
\end{equation}
This directly measures the proportion of tokens that have ``drifted'' beyond an
acceptable range.

\subsection{Maximum Ratio}

\begin{equation}
  w_{\max} = \max_{i} \; w_i
  \label{eq:max_ratio}
\end{equation}

The worst-case importance weight across all tokens in the microbatch. A single
extreme weight can destabilize the gradient estimate even if the average weight
is close to 1.

\section{Implementation}
\label{sec:implementation}
% ══════════════════════════════════════════════

We implement offlineness monitoring directly in SLIME's policy loss function.
The implementation consists of three components:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Metric computation} (\texttt{compute\_offlineness\_metrics()} in
        \texttt{loss.py}, lines 391--427): Takes current and reference
        log-probabilities, applies loss masks to select valid tokens, computes
        all four metrics from the importance weight tensor.

  \item \textbf{Integration with training loop} (\texttt{policy\_loss\_function()}
        in \texttt{loss.py}, lines 697--741): Metrics are computed at the end of
        each microbatch's forward pass and inserted into the loss dictionary for
        logging.

  \item \textbf{CLI flag} (\texttt{arguments.py}): The
        \texttt{-{}-enable-offlineness-metrics} flag gates all computation,
        ensuring zero overhead when monitoring is disabled.
\end{enumerate}

Critically, the reference log-probabilities must come from
\texttt{batch["rollout\_log\_probs"]} (the policy at data generation time), not
\texttt{batch["log\_probs"]} (the policy at the start of the current PPO epoch).
The latter measures only within-epoch drift and is near-zero by construction.

\section{Bug Discovery \& Fixes}
\label{sec:bugs}
% ══════════════════════════════════════════════

Bringing up the offlineness metrics revealed two bugs in the instrumentation
code. Both were discovered, diagnosed, and fixed within a single day
(February~26, 2026). We document them in detail as they illustrate subtle
pitfalls in Megatron's metric aggregation pipeline.

% ── Bug 1 ────────────────────────────────────
\subsection{Bug 1: Wrong Reference Log-Probabilities}

\begin{bugbox}{Bug 1 --- Wrong Reference Log-Probs (Discovered Feb 26)}
\textbf{Symptom}: All offlineness metrics showed near-zero values
  ($D_{\mathrm{mismatch}} = 0$, $\mathrm{clip\_frac} = 0$) in every training step.\\[0.3em]
\textbf{Root cause}: The code compared the current policy's log-probs against
  \texttt{batch["log\_probs"]}, which stores the log-probabilities from the
  \emph{start of the current PPO epoch}---nearly identical to the current policy
  within one epoch. This measured within-epoch drift (effectively zero) rather
  than true offlineness from the rollout policy.\\[0.3em]
\textbf{Impact}: The metrics appeared to show a perfectly on-policy regime,
  masking any actual drift.
\end{bugbox}

\begin{fixbox}{Fix (Commit \texttt{80a3cc6})}
Changed the reference from \texttt{batch["log\_probs"]} to
  \texttt{batch["rollout\_log\_probs"]}, which stores the per-token
  log-probabilities captured at data generation time. After this fix,
  $D_{\mathrm{mismatch}}$ and $\mathrm{clip\_frac}$ became non-zero, but
  $\mathrm{ESS}$ still displayed anomalous values ($\approx 0.19$).
\end{fixbox}

% ── Bug 2 ────────────────────────────────────
\subsection{Bug 2: Metric Reduction Error}

\begin{bugbox}{Bug 2 --- Megatron Reduction Pipeline (Discovered Feb 26)}
\textbf{Symptom}: After fixing Bug~1, the WandB dashboard displayed
  $\mathrm{ESS} \approx 0.19$. However, debug prints inserted into
  \texttt{compute\_offlineness\_metrics()} showed per-microbatch values of
  $\mathrm{ESS} \approx 0.999$. This mathematical contradiction prompted a
  deeper investigation.\\[0.3em]
\textbf{Root cause}: Megatron's training pipeline aggregates metrics by:
  \begin{enumerate}[leftmargin=1.5em, topsep=0.2em]
    \item Packing all metric values into a flat tensor per microbatch:
          $[\texttt{num\_samples},\; m_1,\; m_2,\; \ldots]$
    \item \emph{Summing} across microbatches
    \item Dividing each metric by the total \texttt{num\_samples}
  \end{enumerate}
  This pipeline correctly handles sum-reducible quantities (like total loss or
  sum-of-sample-means). However, our offlineness metrics are \emph{scalar
  averages} (e.g., $\mathrm{ESS} = 0.999$). Inserting a raw scalar into the
  pipeline yields:
  \[
    \frac{0.999 \times 16\;\text{microbatches}}{128\;\text{total samples}}
    \;=\; 0.125
  \]
  which is close to the observed $\approx 0.19$.\\[0.3em]
\textbf{Impact}: All four offlineness metrics were reported at $\sim\!1/8$ of
  their true values, making the policy appear dangerously off-policy when it was
  in fact nearly on-policy.
\end{bugbox}

\begin{fixbox}{Fix (Commit \texttt{ac1de44})}
Before inserting offlineness metrics into \texttt{reported\_loss}, we
  pre-multiply each metric by the microbatch's \texttt{num\_samples}:
  \[
    \texttt{reported\_loss[key]} = \texttt{value} \times \texttt{num\_samples}
  \]
  After the pipeline sums across microbatches and divides by
  \texttt{total\_samples}, the correct weighted average is recovered. Verified:
  ESS now reports $0.996$--$0.999$ consistently.
\end{fixbox}

Several observations emerge from the baseline:

\begin{itemize}[leftmargin=*]
  \item \textbf{Near-perfect on-policyness.} The ESS ratio of $0.9988$ indicates
    that virtually all importance weights are close to~1. The importance sampling
    estimator is as efficient as an on-policy estimator.

  \item \textbf{Negligible mismatch.} The mismatch KL of $6 \times 10^{-4}$ and

    these extremes are isolated ($<\!0.3\%$ of tokens) and do not significantly

    \texttt{kl\_coef=0}, the PPO clip fraction compares \emph{within-epoch}
    ratios (which are trivially near~1 with a single PPO epoch), not rollout
    ratios.

  \item \textbf{Moderate reward level.} The raw reward of 19\% (solve rate)
    suggests the model is in an active learning phase, not fully converged.
\end{itemize}

\section{Key Insight \& Revised Research Direction}
\label{sec:insight}
% ══════════════════════════════════════════════

\begin{keyinsight}
The original hypothesis was that removing the KL penalty ($\lambda_{\mathrm{KL}}
= 0$) would lead to dangerous off-policy drift, as measured by ESS collapse.

\textbf{Finding:} With the standard GRPO configuration (1~PPO epoch per rollout,
$\mathrm{lr} = 10^{-6}$, $\epsilon_{\mathrm{clip}} = 0.2$), the policy remains
\emph{almost perfectly on-policy} ($\mathrm{ESS} \approx 0.999$). The single
PPO epoch and conservative learning rate ensure that the policy barely moves
between data generation and training.

This means the current setup is inherently safe from off-policy degradation---but
also potentially \textbf{underutilizing the rollout data}. Each expensive rollout
batch is used for only one gradient step before being discarded.
\end{keyinsight}

This finding reframes the research question. Rather than asking ``does
offlineness harm GRPO training?'' (answer: not in the default configuration), we
now ask:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Can we deliberately induce offlineness} by increasing data reuse
    (more PPO epochs), raising the learning rate, or reducing rollout frequency?

  \item \textbf{What is the ESS threshold} below which training becomes unstable
    (reward collapse, entropy collapse, gradient explosion)?

  \item \textbf{Can we build an adaptive mechanism} that monitors ESS in real
    time and adjusts PPO epochs or learning rate to stay in a ``sweet spot''---
    maximizing data efficiency while maintaining stability?
\end{enumerate}

\section{Ablation Experiment 1: PPO Epoch Sweep}
\label{sec:ppo_epoch_results}
% ══════════════════════════════════════════════

\subsection{Implementation}

SLIME's original codebase does not support true PPO epochs---it makes a single
pass over each rollout batch. We implemented multi-epoch PPO training by adding a
loop around the \texttt{train()} call in \texttt{actor.py:train\_actor()}
(commit \texttt{6205e02}):

\begin{enumerate}[leftmargin=*]
  \item A new CLI argument \texttt{-{}-ppo-epochs} (default~1) controls the
    number of training passes per rollout.
  \item For each epoch after the first, the data iterators are reset and
    \texttt{log\_probs} are \emph{recomputed} under the updated policy.
    This ensures the PPO importance ratio $w_i = \pi_\theta / \pi_{\mathrm{old}}$
    compares against the epoch-start policy (not the first epoch's policy),
    keeping ratios bounded.
  \item Advantages are \emph{not} recomputed between epochs. For GRPO with
    $\lambda_{\mathrm{KL}} = 0$, advantages depend only on rewards (which are
    fixed for the rollout), so recomputation is unnecessary.
\end{enumerate}

Note the distinction between ``PPO epochs'' and SLIME's existing
\texttt{-{}-num-steps-per-rollout} parameter. The latter \emph{splits} rollout
data into non-overlapping chunks (e.g., 128 samples into 4 batches of 32),
providing only one gradient update per sample. True PPO epochs loop over the
\emph{same} full data $K$ times, providing $K$ gradient updates per sample.

\section{Ablation Experiment 2: Learning Rate Sweep}
\label{sec:lr_sweep_results}
% ══════════════════════════════════════════════

The PPO epoch sweep (Section~\ref{sec:ppo_epoch_results}) revealed that at
$\mathrm{lr} = 10^{-6}$, even 5 training passes over the same data produce no
measurable off-policy drift. This motivated a pivot to \emph{learning rate} as
the primary control knob for offlineness.

\subsection{Checkpoint LR Override Issue}

Changing the learning rate mid-training required resolving a non-trivial
interaction with Megatron's checkpoint loading. All LR sweep experiments resume
from the step-799 checkpoint (trained at $\mathrm{lr} = 10^{-6}$), which stores
both optimizer state and scheduler state.

\begin{bugbox}{LR Override Failure}
\textbf{Initial attempt}: Adding \texttt{-{}-override-opt\_param-scheduler} to
bypass the checkpoint LR assertion. The assertion passed, but training logs
still showed \texttt{lr-pg\_0: 1e-06}---the old learning rate.\\[0.3em]
\textbf{Root cause}: Megatron's \texttt{\_load\_checkpoint\_megatron()} calls
PyTorch's \texttt{optimizer.load\_state\_dict()}, which restores the \texttt{lr}
field in each parameter group from the checkpoint. The scheduler's
\texttt{load\_state\_dict()} correctly overrides \texttt{max\_lr}, but the
optimizer state dict clobbers the \texttt{lr} in the parameter groups
independently.\\[0.3em]
\textbf{Fix}: Use \texttt{-{}-no-load-optim} to skip loading the optimizer and
scheduler state entirely. This initializes a fresh Adam optimizer at the new
learning rate (losing momentum state, which is acceptable for research purposes).
Additionally, each experiment uses a separate \texttt{-{}-save} directory to
prevent checkpoint conflicts between runs.
\end{bugbox}

\subsection{Experiment Configuration}

model weights from the step-799 checkpoint with \texttt{-{}-no-load-optim}.

\subsection{Summary of Findings}

\begin{keyinsight}
\textbf{Finding 1: Standard GRPO is nearly on-policy by construction.}
At the default $\mathrm{lr} = 10^{-6}$ with 1~PPO epoch, ESS $\approx 0.999$
throughout training. The KL penalty ($\lambda_{\mathrm{KL}} = 0$) is unnecessary
because the conservative learning rate already prevents policy drift. Even at
$10\times$ LR ($10^{-5}$) with 3 PPO epochs, ESS remains $>0.998$ for the first
$\sim$100 steps.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 2: Offlineness requires $\geq\!100\times$ baseline LR to manifest.}
At $\mathrm{lr} = 10^{-4}$, ESS drops to 0.899 (transient) or 0.977 (sustained
with 3~epochs). At $\mathrm{lr} = 10^{-5}$, delayed-onset drift appears after
$\sim$100 steps (ESS $\to$ 0.996). Learning rate is the dominant factor; PPO
epochs have negligible effect at low LR.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 3: PPO clipping is structurally ineffective under GRPO.}
Across \emph{all} experiments---including $\mathrm{lr} = 10^{-4}$ where
max\_ratio reaches 12.4---the PPO clip fraction (\texttt{pg\_clipfrac}) is
exactly 0.0. This occurs because GRPO's mean-centered advantages ($r_i -
\bar{r}$) produce positive and negative values that cancel when aggregated via
\texttt{sum\_of\_sample\_mean()}. The clipped and unclipped objectives yield
identical sums.

This means the mechanism that is \emph{supposed} to protect against off-policy
degradation is doing nothing. GRPO's stability relies entirely on the small LR
keeping importance ratios near~1, not on the clipping safeguard.
\end{keyinsight}

\section{Ablation Experiment 3: Rollout Step Sweep (\texttt{num\_steps\_per\_rollout})}
\label{sec:steps_per_rollout_results}
% ══════════════════════════════════════════════

The LR sweep (Section~\ref{sec:lr_sweep_results}) showed that offlineness can be
induced by large learning rates, but at $100\times$ baseline the confounding
effects (entropy collapse, optimizer reset) obscure the signal. This motivated
a search for a \emph{structural} source of offlineness: reusing rollout data
across multiple gradient steps \emph{without} recomputing log-probabilities.

\subsection{Mechanism: \texttt{num\_steps\_per\_rollout} vs.\ PPO Epochs}

SLIME provides a parameter \texttt{-{}-num-steps-per-rollout} ($N$) that splits
each rollout batch into $N$ non-overlapping chunks. The training loop then
performs $N$ sequential gradient steps per rollout, one on each chunk. Crucially,
\textbf{log-probabilities are not recomputed} between steps---the importance
weights $w_i = \pi_\theta / \pi_{\mathrm{old}}$ increasingly deviate from~1 as
the policy updates accumulate within the rollout.

This contrasts with true PPO epochs (Section~\ref{sec:ppo_epoch_results}), where
log-probs are recomputed at the start of each epoch, resetting the importance
ratios. Table~\ref{tab:steps_vs_epochs} summarizes the distinction.

\begin{table}[H]
\centering
\caption{Comparison of \texttt{num\_steps\_per\_rollout} vs.\ PPO epochs.}
\label{tab:steps_vs_epochs}
\begin{tabular}{@{}lcc@{}}
\toprule
\textbf{Property} & \texttt{num\_steps\_per\_rollout} & \textbf{PPO Epochs} \\
\midrule
Data per step       & $1/N$ of rollout (non-overlapping) & Full rollout \\
Steps per rollout   & $N$ & $K$ \\
Log-probs recomputed & No  & Yes (each epoch) \\
Staleness growth     & Monotonic within rollout & Reset each epoch \\
Expected offlineness & Increasing with position & Negligible (at small LR) \\
\bottomrule
\end{tabular}
\end{table}

When \texttt{num\_steps\_per\_rollout}${}= N$, the global batch size is
automatically computed as:
\[
  \texttt{gbs} = \frac{\texttt{rollout\_batch\_size} \times \texttt{n\_samples\_per\_prompt}}{N}
\]
Step numbering follows $\texttt{step} = \texttt{rollout\_id} \times N + \texttt{position}$,
where $\texttt{position} \in \{0, 1, \ldots, N{-}1\}$.

At the baseline learning rate, neither $N=2$ nor $N=4$ produced any measurable

rollout. This is consistent with the PPO epoch results: at $\mathrm{lr} = 10^{-6}$,
each gradient step moves the policy so little that even stale log-probabilities
remain accurate.

mechanism---data staleness---that is directly relevant to practical RLHF
training. The within-rollout ESS gradient with rollout-boundary resets is
strong causal evidence that stale log-probabilities degrade importance sampling
quality.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 5: PPO clipping activates under genuine offlineness.} The
nonzero \texttt{pg\_clipfrac} at later positions ($\sim$0.004) contrasts with
the exact-zero clipping seen in all previous experiments. This suggests that
data-staleness-induced offlineness produces a qualitatively different
importance weight distribution than LR-shock-induced offlineness, one where the
clipping mechanism actually engages.
\end{keyinsight}

catastrophic failure. The mechanism is not broken---the default threshold is
simply too loose to activate under GRPO's typical importance weight
distribution. GRPO's apparent safety is a narrow coincidence: the default LR
keeps ratios just below $\epsilon = 0.2$, creating the illusion that clipping
is unnecessary.
\end{keyinsight}

\section{Ablation Experiment 5: PPO Ratio Reference Point (\texttt{-{}-use-rollout-logprobs})}
\label{sec:rollout_logprobs_results}
% ══════════════════════════════════════════════

The clipping sweep (Section~\ref{sec:clip_sweep_results}) revealed that clipping is
necessary but normally inactive. A deeper code analysis uncovered the
\textbf{root cause}: the PPO importance ratio in the loss function uses
\texttt{batch["log\_probs"]} (recomputed by the current actor at the start of
each training step), \emph{not} \texttt{batch["rollout\_log\_probs"]} (from the
original data generation). Since \texttt{log\_probs} is always fresh, the PPO
ratio $w = \pi_\theta / \pi_{\mathrm{old}}$ is always near~1---regardless of
how stale the rollout data is. The offlineness metrics, by contrast, compare
against \texttt{rollout\_log\_probs}, which is why they detect drift
(max\_ratio $= 12.4$) that the loss function never sees.

This means the earlier hypothesis---that PPO clipping is inactive because
GRPO's mean-centered advantages cancel under aggregation---was \textbf{incorrect}.
Advantages are not mean-centered (\texttt{-{}-normalize-advantages} defaults to
False). The real cause is that the PPO ratio never reflects true data staleness
because it uses a freshly recomputed reference.

\subsection{Experiment Design}

SLIME provides \texttt{-{}-use-rollout-logprobs}, which substitutes
\texttt{batch["rollout\_log\_probs"]} as the old-policy reference in the PPO
loss. This makes the PPO ratio reflect the same staleness that offlineness
metrics measure. We ran the identical steps=8, $\mathrm{lr} = 10^{-5}$
configuration with this flag enabled:

Key observations:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Clipping is uniformly active.} Unlike the baseline where
    \texttt{pg\_clipfrac} was exactly~0 at positions 1--6, the rollout-logprobs
    experiment shows nonzero clipping at \emph{every} position, with a
    monotonically increasing gradient from 0.0001 (position~1) to 0.0022
    (position~8). This confirms that using fresh log-probs as the PPO reference
    was masking the true offlineness from the loss function.

  \item \textbf{Magnitude is modest.} Even with stale log-probs, clipping
    engages at only 0.01--0.2\% of tokens. The $\epsilon = 0.2$ threshold
    remains rarely exceeded because the per-step policy movement is small at
    $\mathrm{lr} = 10^{-5}$. This explains why the clipping sweep
    (Section~\ref{sec:clip_sweep_results}) found that tightening
    $\epsilon$ to 0.05 only increased clipfrac to 1--2\%.

  \item \textbf{ESS gradient is preserved.} The within-rollout ESS gradient
    (0.999 $\to$ 0.997) is nearly identical to the baseline experiment,
    suggesting that using rollout log-probs in the loss does not
    significantly alter the training dynamics at this scale.

  \item \textbf{Late-run drift.} Average clipfrac increases from 0.0006
    (early) to 0.0013 (late), and ESS drifts from 0.999 to 0.998, consistent
    with gradual policy drift over $\sim$200 rollouts.
\end{enumerate}

\begin{keyinsight}
\textbf{Finding 9: PPO clipping inactivity has two independent causes.}
(a)~The PPO ratio uses freshly recomputed log-probs, not the stale rollout
log-probs, so the ratio is always near~1 regardless of data age. Enabling
\texttt{-{}-use-rollout-logprobs} makes clipping nonzero at all positions.
(b)~Even with stale log-probs, the conservative LR keeps ratios below
$\epsilon = 0.2$ most of the time, so clipping engages at $<$0.3\% of tokens.
Both factors must be addressed for PPO clipping to function as intended under
GRPO.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 10 (Corrected mechanism): Advantages are NOT mean-centered in
standard GRPO.} \texttt{-{}-normalize-advantages} defaults to False and is not
used in our configurations. The original hypothesis that mean-centered
advantages cancel under \texttt{sum\_of\_sample\_mean()} aggregation (Finding~3)
was \textbf{incorrect}. The true cause of \texttt{pg\_clipfrac} $= 0$ is that
the PPO loss uses freshly recomputed \texttt{batch["log\_probs"]} rather than
the stale \texttt{batch["rollout\_log\_probs"]}. This is a more fundamental
issue: GRPO's PPO-style clipping is architecturally disconnected from data
staleness because the importance ratio never reflects the actual age of the
training data.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 11: Stale log-probs + tight clipping is a prescriptive fix
for GRPO's clipping failure.} When the PPO ratio uses rollout log-probs
(\texttt{-{}-use-rollout-logprobs}) and the clipping threshold is
tightened ($\epsilon = 0.05$), the resulting configuration produces
\emph{increasing entropy} (0.28 $\to$ 1.19), \emph{improving reward}
(0.18 $\to$ 0.20), and \emph{stable ESS} (0.997+). This is the only
configuration that makes PPO clipping function as its designers intended:
constraining large policy updates while allowing exploration. The entropy
increase suggests that clipping prevents the policy from collapsing into
narrow modes, maintaining output diversity.
\end{keyinsight}

\begin{keyinsight}
\textbf{Finding 12: The $2 \times 2$ factorial reveals a synergy, not
just an additive effect.} Neither stale log-probs alone (Ablation~5:
clipping at 0.2\%, entropy not tracked long enough) nor tight clipping
alone (Ablation~4: entropy declines 0.20 $\to$ 0.08) produce the
entropy-increasing behavior. It requires \emph{both} stale log-probs
\emph{and} tight clipping acting together. The stale log-probs make the
PPO ratio reflect genuine offlineness; the tight clipping aggressively
constrains the resulting large updates; the combined effect prevents
mode collapse and promotes exploration. This interaction effect would be
invisible without the full factorial design.
\end{keyinsight}

\section{Consolidated Findings}
\label{sec:findings}
% ══════════════════════════════════════════════

This section synthesizes the twelve key findings from six rounds of ablation
experiments into a coherent picture of GRPO's offlineness behavior.

\subsection{The Central Result: GRPO Is On-Policy by Construction}

Standard GRPO with $\mathrm{lr} = 10^{-6}$ maintains ESS $\approx 0.999$
throughout training. This holds regardless of:
\begin{itemize}[leftmargin=*]
  \item PPO epochs (1, 3, or 5 passes over the same data),
  \item \texttt{num\_steps\_per\_rollout} (2 or 4 chunks per rollout), or
  \item Training phase (step 600+ or step 800+).
\end{itemize}
The conservative learning rate ensures each gradient step moves the policy
by so little that importance weights remain near~1. The KL penalty
($\lambda_{\mathrm{KL}} = 0$) is unnecessary---not by design, but because the
LR already prevents drift.

\subsection{Three Paths to Offlineness}

We identified three mechanisms to induce measurable offlineness, with
qualitatively different characteristics:

\begin{table}[H]
\centering
\caption{Comparison of three offlineness-inducing mechanisms.}
\label{tab:three_paths}
\begin{tabular}{@{}p{3cm}ccp{4.5cm}@{}}
\toprule
\textbf{Method} & \textbf{Min ESS} & \textbf{Clean?} & \textbf{Problem} \\
\midrule
PPO epochs (3--5) at lr=$10^{-6}$ & 0.999 & --- & No effect: log-probs recomputed each epoch \\
LR $= 10^{-4}$ ($100\times$) & 0.899 & No & Entropy collapse, optimizer reset confound \\
LR $= 10^{-5}$ ($10\times$) + 1 epoch & 0.996 & Partial & Delayed onset after $\sim$100 steps; slow \\
\textbf{steps=8 + lr=$10^{-5}$} & \textbf{0.988} & \textbf{Yes} & Long-run entropy decline (0.16$\to$0.07) \\

\end{tabular}
\end{table}

The \texttt{num\_steps\_per\_rollout}${}= 8$ experiment is the only one that
produces \emph{structurally interpretable} offlineness: a within-rollout ESS
gradient caused by data staleness, with rollout-boundary resets providing
causal evidence.

\subsection{PPO Clipping: Two Independent Causes of Inactivity}

Our initial finding was that \texttt{pg\_clipfrac} $= 0$ across all experiments
at $\epsilon = 0.2$, even when max\_ratio reached 12.4. Code analysis
(Section~\ref{sec:rollout_logprobs_results}) revealed the root cause: the PPO
loss uses freshly recomputed \texttt{batch["log\_probs"]} as its reference,
\emph{not} the stale \texttt{batch["rollout\_log\_probs"]}. The offlineness
metrics detect drift (max\_ratio $= 12.4$) because they compare against
rollout log-probs, but the loss function sees a near-unity ratio.

Enabling \texttt{-{}-use-rollout-logprobs} makes clipping nonzero at all
positions (0.0001--0.0022), confirming that the PPO ratio's reference point
is the primary cause of clipping inactivity.

The clipping sweep (Section~\ref{sec:clip_sweep_results}) provided the second
piece: even with stale log-probs, the conservative LR keeps ratios below
$\epsilon = 0.2$ most of the time. Removing clipping entirely ($\epsilon = 10^6$)
caused \textbf{catastrophic collapse} within $\sim$50 rollouts, while
tightening to $\epsilon = 0.05$ activated clipping at 1--2\%.

GRPO's clipping inactivity thus has \textbf{two independent causes}:
(1)~the PPO ratio uses fresh log-probs, disconnecting it from data staleness;
(2)~even when using stale log-probs, the conservative LR keeps ratios small.
Both must be addressed for clipping to function as intended.

\subsection{A Stability Boundary Exists}

The comparison between $N = 4$ (stable, reward improving) and $N = 8$ (entropy
declining, reward degrading) at the same $\mathrm{lr} = 10^{-5}$ reveals a
practical stability boundary. Even though the per-step ESS drop is only
$\sim$1\%, its cumulative effect over hundreds of rollouts degrades model
quality. This implies that offlineness monitoring (ESS, entropy) could serve as
an \emph{early warning system} for training instability.

\subsection{The Prescriptive Fix: Stale Log-Probs + Tight Clipping}

The $2 \times 2$ factorial (Section~\ref{sec:factorial_results}) reveals
that combining \texttt{-{}-use-rollout-logprobs} with $\epsilon = 0.05$
is the only configuration that produces \emph{increasing} entropy
(0.28 $\to$ 1.19) and \emph{improving} reward (0.18 $\to$ 0.20). This
synergistic interaction transforms PPO clipping from an inactive safety
mechanism into an effective exploration-promoting constraint. Neither
component alone produces this effect: stale log-probs without tight
clipping accelerates collapse; tight clipping without stale log-probs
slows but does not prevent entropy decline.

\section{Assessment \& Discussion}
\label{sec:assessment}
% ══════════════════════════════════════════════

\subsection{Strengths}

\begin{itemize}[leftmargin=*]
  \item \textbf{Clean causal mechanism.} The within-rollout ESS gradient with
    rollout-boundary resets is strong evidence for data-staleness causation,
    not merely correlation with LR changes.

  \item \textbf{The clipping story is now complete---with a fix.} We have a
    full $2 \times 2$ factorial (fresh/stale log-probs $\times$
    tight/no clipping) plus individual ablations. Clipping is (a)~inactive at
    default settings due to fresh log-prob references, (b)~catastrophically
    needed when removed, (c)~activatable by tightening the threshold or
    using stale log-probs, and (d)~\textbf{a prescriptive fix when both
    corrections are combined}: stale log-probs + $\epsilon = 0.05$ is the
    only configuration that produces entropy increase and reward improvement.
    This elevates the contribution from diagnosis to prescription.

  \item \textbf{Self-correcting methodology.} The original hypothesis
    (mean-centered advantages cancel under aggregation) was empirically
    refuted by code analysis and the rollout-logprobs experiment, leading
    to a more precise mechanistic understanding (Finding~10).

  \item \textbf{Practical stability boundary.} The $N = 4$ vs.\ $N = 8$
    divergence has direct engineering implications for RLHF practitioners
    choosing data reuse strategies.

  \item \textbf{Coherent narrative.} The ten findings build a logical
    progression: GRPO is on-policy $\to$ because LR is tiny $\to$ clipping
    never activates (PPO ratio uses fresh log-probs) $\to$ data reuse creates
    real offlineness $\to$ without clipping the system collapses $\to$ the
    default setup is a narrow coincidence of LR, $\epsilon$, and log-prob
    reference point.
\end{itemize}

\subsection{Limitations}

\begin{itemize}[leftmargin=*]
  \item \textbf{The offlineness magnitude is small.} Even in the ``breakthrough''
    experiment, ESS only drops to 0.988 (1.2\% reduction). The practical
    consequences manifest as gradual entropy decline rather than dramatic
    failure (except when clipping is removed entirely).

  \item \textbf{Single model, single dataset.} All experiments use
    Qwen2.5-Math-1.5B on math reasoning. Generalization to other model sizes,
    domains, and reward functions is unverified.

  \item \textbf{Checkpoint-resume artifacts.} All experiments resume from
    step~799 with \texttt{-{}-no-load-optim}, losing Adam momentum. Offlineness
    dynamics during early training (from step~0) may differ.

  \item \textbf{The no-clip collapse may be partially a mean-centering
    artifact.} A formal analysis of how \texttt{sum\_of\_sample\_mean}
    interacts with clipping, plus per-sample statistics before aggregation,
    would strengthen the theoretical explanation.
\end{itemize}

\section{Autoresearch Experiments: LR Robustness of the Prescriptive Fix}
\label{sec:autoresearch}
% ══════════════════════════════════════════════

Following the six manual ablations, an autonomous experiment pipeline was
deployed to test the robustness and generalizability of the prescriptive fix
(Finding~11--12). The key question: \emph{is the stale-logprobs + tight-clip
fix robust to higher learning rates?}

\subsection{Experiment 001: Prescriptive Fix at lr=$5 \times 10^{-5}$}

\paragraph{Setup.} Identical to the proven fix (stale log-probs, $\epsilon = 0.05$,
$N = 8$ steps) but with lr increased from $10^{-5}$ to $5 \times 10^{-5}$---a
$5\times$ increase. Run for 50 rollouts (800--850) from the iter-799 checkpoint
with \texttt{-{}-no-load-optim}.

\paragraph{Results.}
\begin{itemize}[leftmargin=*]
  \item \textbf{Rollouts 800--810}: Entropy 0.13--0.31, ESS 0.986--0.999,
    pg\_clipfrac 0.01--0.04, max\_ratio 2.0--4.1. Appeared healthy.
  \item \textbf{Rollouts 820--835}: Entropy surged to 1.89 (step 6734), ESS
    dropped to 0.927, max\_ratio hit 8.5, clip\_frac\_02 reached 21\%.
  \item \textbf{Rollouts 848--850}: \textbf{Total collapse.} All rewards $= 0$.
    Model generated degenerate repetitive outputs (``n n n n\ldots'').
    88\% of responses truncated at max length.
\end{itemize}

\begin{keyinsight}
\textbf{Finding 13:} At lr=$5 \times 10^{-5}$, the prescriptive fix causes
\emph{entropy explosion followed by mode collapse}. Entropy rises $10\times$
faster than at lr=$10^{-5}$ (reaching 1.89 vs.\ 1.19 at the proven LR), but
overshoots into a degenerate distribution where the model loses all math
reasoning capability. The LR boundary for the fix lies between $10^{-5}$ and
$5 \times 10^{-5}$.
\end{keyinsight}

\subsection{Experiment 002: Tighter Clipping ($\epsilon = 0.02$) at lr=$5 \times 10^{-5}$}

\paragraph{Setup.} Same as Experiment~001 but with $\epsilon = 0.02$
(vs.\ $\epsilon = 0.05$). Tests whether tighter clipping can rescue the fix at
higher LR.

\paragraph{Results.}
\begin{itemize}[leftmargin=*]
  \item Entropy stayed controlled (0.08--0.38), never exploding.
  \item ESS remained above 0.98 (vs.\ dropping to 0.927 at $\epsilon = 0.05$).
  \item However, raw\_reward \textbf{still degraded}: $0.055 \to 0.008$ over
    46 rollouts. Truncation rate climbed from 16\% to 76\%.
  \item The model's math solving capability decreased even with controlled
    entropy.
\end{itemize}

\begin{keyinsight}
\textbf{Finding 14:} Tighter clipping ($\epsilon = 0.02$) \emph{delays but does
not prevent} degradation at lr=$5 \times 10^{-5}$. The problem is not just
entropy explosion (which clipping can contain). The accumulated policy drift from
large per-step updates moves the model away from useful reasoning even when
individual updates are clipped. The prescriptive fix requires
lr $\lesssim 10^{-5}$ regardless of $\epsilon$.
\end{keyinsight}

\subsection{Implications for the Core Thesis}

The autoresearch experiments refine the prescriptive fix narrative:

\begin{quote}
The stale-logprobs + tight-clip fix is \textbf{effective but LR-sensitive}. At
the conservative lr=$10^{-5}$ used in standard GRPO training, it produces
healthy entropy increase and reward improvement. At higher learning rates, two
failure modes emerge: (1) $\epsilon = 0.05$ allows entropy explosion $\to$ mode
collapse, and (2) even $\epsilon = 0.02$ cannot prevent capability degradation
from accumulated drift.

This LR sensitivity is consistent with the core thesis: GRPO's stability
depends on the conservative learning rate keeping training implicitly on-policy.
The prescriptive fix works precisely because it operates within this stability
region while correcting the log-prob reference. Attempting to use the fix as a
license to increase LR negates its benefits.
\end{quote}


\section{Open Questions \& Next Steps}
\label{sec:next}
% ══════════════════════════════════════════════

\subsection{Completed Ablation Summary}

Six ablation rounds have been completed:
\begin{enumerate}[leftmargin=*]
  \item \textbf{PPO epoch sweep} (epochs = 1, 3, 5): No effect at lr=$10^{-6}$.
  \item \textbf{Learning rate sweep} (lr = $10^{-6}$, $10^{-5}$, $10^{-4}$):
    LR is the dominant offlineness lever; $10^{-4}$ confounded by entropy collapse.
  \item \textbf{Rollout step sweep} ($N$ = 2, 4, 8 at lr=$10^{-5}$, $10^{-6}$):
    $N = 8$ + lr=$10^{-5}$ produces clean within-rollout offlineness gradient.
  \item \textbf{Clipping threshold sweep} ($\epsilon$ = 0.05, 0.2, $\infty$):
    Clipping is necessary (no-clip collapses) but insufficient (tight clip
    still degrades).
  \item \textbf{PPO ratio reference point} (\texttt{-{}-use-rollout-logprobs}):
    Using stale rollout log-probs makes clipping nonzero at all positions;
    corrects the mechanism explanation for Finding~3.
  \item \textbf{$2 \times 2$ factorial} (stale log-probs $\times$ clipping):
    Stale log-probs + tight clipping ($\epsilon = 0.05$) is a prescriptive fix
    that produces entropy increase and reward improvement (Finding~11--12).
\end{enumerate}

\subsection{Remaining Candidate Experiments}

\begin{enumerate}[leftmargin=*]
  \item \textbf{Finer $N$ sweep} ($N \in \{5, 6, 7\}$ at lr=$10^{-5}$):
    Narrow the stability boundary between $N = 4$ (stable) and $N = 8$
    (degrading).

  \item \textbf{Non-mean-centered advantages}: Skip mean-centering
    ($r_i$ instead of $r_i - \bar{r}$) and repeat the steps=8 experiment.
    Would confirm whether the clipping inactivity is caused by advantage
    cancellation under aggregation.

  \item \textbf{Train from step~0}: Study offlineness during early rapid
    learning rather than the stabilized phase (step~800+).

  \item \textbf{Adaptive \texttt{num\_steps\_per\_rollout}}: Use ESS/entropy
    monitoring to dynamically adjust $N$, staying below the stability boundary
    while maximizing data efficiency.
\end{enumerate}

\subsection{Research Direction}

The twelve findings support a coherent narrative suitable for a research
contribution:

\begin{quote}
\textbf{Thesis:} GRPO's stability does not come from its PPO clipping mechanism
but from two coincidences: (1)~the conservative learning rate keeps training
implicitly on-policy, and (2)~the PPO importance ratio uses freshly recomputed
log-probs rather than the stale rollout log-probs, architecturally disconnecting
clipping from data staleness. Once genuine offlineness is introduced via data
reuse, the existing safeguards are either inactive ($\epsilon = 0.2$ never
triggers because the ratio reference is always fresh) or insufficient (tighter
$\epsilon$ slows but does not prevent degradation). Removing clipping entirely
confirms its necessity through catastrophic collapse.

However, \textbf{a prescriptive fix exists}: combining stale rollout log-probs
as the PPO reference with tight clipping ($\epsilon = 0.05$) produces the only
configuration where entropy \emph{increases} (0.28 $\to$ 1.19, a $4\times$
rise) and reward improves---suggesting that properly functioning PPO clipping
promotes exploration rather than merely preventing collapse. This synergistic
interaction (neither factor alone is sufficient) demonstrates that GRPO's
clipping mechanism can work as intended when its two architectural flaws are
corrected.
\end{quote}

This narrative connects to broader concerns about RLHF stability as
practitioners pursue more aggressive data reuse for efficiency, and explains
why recent algorithms (DAPO, Dr.~GRPO) have redesigned the clipping mechanism
rather than relying on the standard PPO formulation. Our prescriptive fix
suggests an alternative path: rather than abandoning PPO clipping, one can
repair it by using the correct reference log-probs.

\subsection{Megatron Metric Reduction Pipeline}

The Megatron training loop processes data in microbatches. For each microbatch,
the loss function returns a dictionary \texttt{reported\_loss} containing metric
tensors. These are packed into a flat tensor:
\[
  \texttt{values} = [\texttt{num\_samples},\; m_1,\; m_2,\; \ldots]
\]
Across microbatches, values are \emph{summed}. An \texttt{all\_reduce} aggregates
across data-parallel ranks. Finally, each metric is computed as:
\[
  \hat{m}_k = \frac{\texttt{values}[k]}{\texttt{values}[0]} \times \texttt{cp\_size}
\]
where $\texttt{values}[0]$ is the total \texttt{num\_samples}. This design
assumes that each $m_k$ was originally a ``sum-of-sample-means'' (as produced by
\texttt{sum\_of\_sample\_mean()} for losses). For scalar-average metrics like
ESS, we must pre-multiply by $\texttt{num\_samples}$ per microbatch to ensure
correctness.

\subsection{Cluster Infrastructure}

Experiments run on the USC CARC Endeavour cluster (\texttt{nlp} partition).
Notable operational details:

\begin{itemize}[leftmargin=*]
  \item Nodes \texttt{c05-05} and \texttt{c06-05} have broken CUDA drivers
    (Error 802); always excluded via \texttt{-{}-exclude}.
  \item The NLP partition supports preemption---jobs can be killed by
    higher-priority users. Experiments must be designed to resume from
    checkpoints.
  \item Job management is fully automated via \texttt{sbatch} scripts that
    include \texttt{pip install -e .} for code synchronization.
\end{itemize}
